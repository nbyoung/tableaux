# Design 9f3f: Subproject linkage

The linkage rule of 2026-09-30 (F3, F5, F12) stands on the trunk at language 0.3.0. This design covers what remains, in five parts. A task names its subproject once, in a task-level `subproject` field that stands for a recursive junction at every gate after its definition, and a parent may not carry it (F4; decisions 1 to 3, 10 and 11). A `Reaffirmed:` trailer on a task with no status of its own to confirm draws a warning, and README.md's example stops making one (F13; decision 4). A cross-project requirement on an absolute URL may state no `commit`, reads the other project's trunk tip, and the audit marks it unpinned as information (F26; decision 5). A subproject whose language lags its parent's, patch included, draws a warning (F25; decisions 6 and 7). The history's schema and fields gain the key `subproject`, and VIEWS.md places a subproject's events inline, as tablo's design 8ed1 and the corpus already do (decision 8). F4 and F26 raise the language to 0.4.0, and the rest ride on it (decision 9). D*n* below is decision *n* under [Decisions at review](#decisions-at-review).

## F4 Wholesale delegation

**The problem.** PLAN.md's F4 (PLAN.md:219): each of `77b2`, `6103`, `c6e8` and `595e` states `{ subproject: { url: subprojects/<name> } }` at eight gates, and the corpus entry `submodule-subproject` states it at ten. The method has no shorthand, and a recursive junction does not inherit (README.md#junctions), so no parent can state it once.

**The rule (D1).** A task file gains an optional field `subproject`, placed between `requires` and `junctions`, in the `$defs/subproject` form a junction uses: `url`, `id` defaulting to that project's root, and `commit` by the `url`'s form. The field stands for a recursive junction at each gate after the first gate that follows `undefined`: `defined` in every gate set SYNTAX.md, this repository and the corpus use. The rule reads the position and not the key, since `gates.yaml` names `undefined` alone. At a covered gate the junction resolves:

1. from the task's own entry there, of any kind: a not-applicable entry exempts the gate, a plain entry makes it the task's own work, inheriting field by field as any plain entry does, and a recursive entry names another task or project;
2. else from the field, as a recursive junction whose `source` is the task itself.

Either way the task's own file decides the kind at the gate. Where the field decides it, the junction is recursive, so the field lifts an ancestor's exemption, as a stated recursive entry does today, and takes no field of an ancestor's plain entry. A plain entry the task states inherits as any plain entry does. F7's rule stands unchanged: the field is the descendant's own entry.

**The status file (D2).** Nothing changes. Where the next junction is the field's, S9 and S10 read it as recursive, so the file holds only the gate, and the contributor advances the gate as the subproject's task completes each one, in the commit that moves the pin, as the umbrella's `3713cd2` does. At `undefined` the next junction is `defined`, plain, so the file states a state as before.

**A parent (D3).** A parent has no status and its junctions are defaults; the field names one task's work, as a recursive junction does. A validator rejects it on a parent (J18), and no child inherits it.

**Example.** The umbrella's `77b2`, before and after; every derived fact, the tooling entry's among them, stays as it is:

```yaml
# tasks/77b2.yaml on main, below its requires
junctions:
  mockup:         { subproject: { url: subprojects/tablo } }
  function:       { subproject: { url: subprojects/tablo } }
  design:         { subproject: { url: subprojects/tablo } }
  implementation: { subproject: { url: subprojects/tablo } }
  unit:           { subproject: { url: subprojects/tablo } }
  integrate:      { subproject: { url: subprojects/tablo } }
  validate:       { subproject: { url: subprojects/tablo } }
  release:        { subproject: { url: subprojects/tablo } }
```

```yaml
# tasks/77b2.yaml with the field, below its requires
subproject: { url: subprojects/tablo }
```

The corpus entry `subproject-field` (T1) is `submodule-subproject` in this form. It adds two own entries and an ancestor's exemption:

```yaml
# tasks/c000.yaml, the root
junctions:
  performance: { applies: false }
```

```yaml
# tasks/c100.yaml, the leaf
subproject: { url: sub }
junctions:
  reliability: { applies: false }                  # replaces the field
  release:     { contributor: olive@example.org }  # replaces the field
```

It resolves to recursive at eight gates, `performance` among them, exempt at `reliability` and plain at `release`, with the junctions, status, pins and events of `submodule-subproject`.

**The text change.** README.md#junctions gains the paragraph before the one on inheritance, and that paragraph's last sentence names the field. README.md#history names the field among what a pin event reads. SYNTAX.md's task schema and fields table gain the field, the `subproject` table names a task beside a junction and a requirement, and a new example, `tasks/5e6f.yaml`, shows the field with an own entry at `release`.

**The validator rules.** J18, error: "No task-level `subproject` on a parent". Source: README Junctions, "a validator rejects one on a parent, and a task-level `subproject` field there too". Entry `subproject-field-on-parent` (T2). The field takes J7 to J9 and J13 to J17 as a junction's `subproject` does, J15 included, and R12 reads it as a junction; its findings name the task and the file without a gate, as a requirement's do (RULES.md's new paragraph under the junctions table).

**What tablo does today.** `model.Task` (`internal/model/model.go:88`) has no such field, and the schema rejects the key: the trial reports `T3 … subproject is no field of the file` and, with no recursive junction at `design`, `S10` on `status/c100.yaml`. `derive.resolve` (`internal/derive/junction.go:282`) returns at once for the task's own recursive entry and skips an ancestor's (line 296), and `resolved` (line 215) builds the snapshot from `entry(task, gate).Subproject` (line 228). The changes:

- `4f60` Loader: `model.Task` gains `Subproject`, read as a junction's; `subprojects` (`internal/load/build.go:180`) adds it, so its link resolves with the others.
- `27a3` Derivation: `resolve` takes the field after the task's own entry at each gate from index 2 on; `resolved` takes the snapshot's field from it; `fields` (`internal/derive/events.go:333`) and `naming` add it, so its pin moves are pin events.
- `8118` Validator: the embedded task schema accepts it; J18 stands beside `j3` (`internal/validate/junctions.go:88`); `subproject` (line 29) runs on the field with no gate; R12 reads it.

**What the front ends meet.** Nothing: they read resolved junctions from tablo. tabloio's `propose` (b618) may write the field; no design asks it to.

**The version effect.** A field appears that older content still satisfies: minor.

**The alternative.** A wildcard junction key, `"*"`, says the same in the `junctions` map, and loses: every junction key names a gate (J1), and a key that names none breaks that rule for one case.

## F13 A reaffirmation of a recursive junction is moot

**The problem.** README.md:122 reaffirms `c07d`, whose next junction, `implementation`, is recursive, so its date and recorder come from `f1a0` at the pin (README.md#status). A parent derives its date from its children the same way. Neither has a status of its own to confirm, so a `Reaffirmed:` trailer naming one changes no derived fact (corpus/README.md:196).

**The rule (D4).** The example drops `--trailer 'Reaffirmed: c07d'` and keeps `Reaffirmed: 9f31`, which the weather station's `W13` makes. README.md#status says what such a trailer does, and a rule reports it. The history keeps the `reaffirmed` event, since an event is any commit whose trailer names the task (README.md#history). The rule reads the files at the trailer's commit: the task is a parent there, or a leaf whose next applicable junction after its status file's gate is recursive. A leaf with no status file stays out until 7166 decides F17 ([Meeting points](#meeting-points)).

```

```

In the entry `reaffirmed-snapshot` (T3), `b2c9`'s next junction is recursive and `e4a1` is the root: two H7 warnings, two `reaffirmed` events, and every date and recorder as before.

**The text change.** README.md#status, "Date and recorder", gains one sentence, and its example loses the second trailer.

**What the front ends meet.** tabloio's `reaffirm` (b618) and tablotui's action (518e) may decline a task that H7 would report; no design asks them to.

**The version effect.** A new finding that clarifies meaning: patch alone, as 0.3.1 was.

**The alternative.** A meaning for the trailer, the date the parent last confirmed the snapshot it reads, adds a second date to every snapshot and to every view that shows one, for a fact the pin event already records.

## F26 A requirement on a sibling needs a commit before the work exists

**The problem.** README.md:55 resolves F26 in text: the requirement lives in the dependent task's design until a commit shows the result. The audit cannot see it there. tablotui's `518e` met the error first: decision 15 records validator finding R1 on a local `id`, moves the requirement into the design, and later inserts it with tabloio's commit `d443471`. tabloio's `b618` decision 12 keeps three tablo requirements in its plan paragraph, and its file now names them at `03c5e35`.

**The rule (D5).** On an absolute URL, `commit` is optional in a requirement alone; on a junction and on the task-level field it stays required (J15). An entry that states none is **unpinned**:

- A tool reads the originating project at the tip of its trunk, in the clone the URL maps to, by the Loader's mapping or its cache. The trunk is the one `version.yaml` names at the clone's default branch (`refs/remotes/origin/HEAD`, else `HEAD`), resolved remote-tracking branch first, as README.md#project orders a linked repository. Without a mapping, a fetch brings the default branch.
- The condition, R9 and the blockage tree read the task at that tip. R13 stays silent, since the commit read is the tip.
- The audit reports the entry as information (R14) until the contributor states the commit, at the first status commit after the originating task reaches `from`. That change is a `pin` event with no `old`.
- A junction never takes the form, since every reader of one commit must see one subproject, and a status derives from it; a requirement's condition only warns.

```yaml
# tabloio's tasks/b618.yaml, written before tablo's 4ed9 reached implementation
requires:
  - { subproject: { url: https://github.com/nbyoung/tablo, id: "4ed9" }, from: implementation, to: integrate,
      text: The library's trailer lines and the views the plans read }
```

**The finding's four parts, confirmed or amended.** The minor version 0.4.0: confirmed. A schema change: amended to none, since the schema states no `commit` requirement; J15 is a validator rule, and the schema accepts the form today. A rule: R14, information. A corpus entry: `requires-unpinned` (T4). A Loader change: confirmed, in `4f60`, with a Validator change in `8118` beside it.

**The text change.** README.md#tasks replaces the sentences on the design paragraph with the unpinned entry; the cross-project paragraph says where an unpinned entry reads and that the audit reports it; README.md#junctions narrows the required `commit` to a junction's. SYNTAX.md's `subproject` table narrows `commit`, its `old` and `pin` rows name a first-stated commit, and the `f1a0` example gains an unpinned entry.

**The audit rule.** R14, information: "A cross-project requirement on an absolute URL that states no `commit`: unpinned, read at the tip of the originating project's trunk". Source: README Tasks, "It reports an unpinned entry as information, since its condition moves with the other project's trunk". Information, as H4: nothing is wrong, and the reader learns that two clones may disagree. J15's row narrows to a junction or a task's field, and RULES.md's paragraph under the requires table says J15 does not apply to a requirement.

**What tablo does today.** `resolve` (`internal/load/link.go:84`) sets `BadCommit` on any absolute URL without a full hash, and `j15` (`internal/validate/junctions.go:166`) fires for a requirement as for a junction. The trial reports `J15 … states no commit` and no condition. The changes:

- `4f60` Loader: a requirement's field with no `commit` resolves at the trunk tip above. `model.Link` gains `Unpinned`, and its target key keeps it apart from a pinned link to the same URL. The Loader learns each field's origin, since a requirement and the task-level field both pass no gate.
- `8118` Validator: `j15` skips a requirement's field, and R14 joins `internal/validate/requires.go`.
- `27a3` Derivation: none for the condition, which reads `Link.Commit`. The pin event of a first-stated commit already takes `old` from the previous file (`internal/derive/events.go:394`); a test fixes it.

**What the front ends meet.** `518e` and `b618` may write their requirements unpinned before the commit exists, and their designs' paragraphs may then shrink to the entry. Validation of any absolute URL still needs a mapped clone or the network (`4b4f` decision 6).

**The version effect.** A form appears that older content satisfies and an older tool rejects (J15): minor, 0.4.0.

**The alternative.** The text's resolution of 2026-10-06 stands as the alternative: the requirement waits in the design, where no tool sees it, and an agent that writes it early meets R1 or J15, as `518e` did.

## F25 A subproject's language falls behind its parent's

**The problem.** PLAN.md:228: at the review of 2026-10-06 the umbrella stood at 0.3.1, tablo at 0.3.0 and the front ends at 0.2.0. A language before 0.2.1 exempts a commit from H6 (`internal/validate/derived.go:393`), so the lag silently exempted them. The lag recurs today: the umbrella states 0.3.2, and all four pins and the `corpus/tooling` tag read 0.3.1.

**The rule (D6).** J19, warning. A validator compares the `version.yaml` of each project that a recursive junction or the task-level field names, read at the commit the linkage fixes, with the project's own, and warns when it is before it. The comparison takes major, minor and patch, since a patch can change what a rule reads: H6's exemption ends at 0.2.1. The rule reads the three forms alike: a submodule at its pin, a same-repository path at the parent's commit, and an absolute URL at its `commit`. It leaves out a cross-project requirement, which reads one task's gate and delegates no work, so an upward requirement on an old commit of the parent warns of nothing. It reports once per task and linkage, without a gate, however many junctions name the linkage. It stays silent where the other project states no version the tool can read; P2, P3 or J8 report that. It applies whatever version the parent states (D7).

```
.tableaux/tasks/b2c9.yaml: warning: J19 The project at behind states tableaux 0.3.1, before this project's 0.3.2
```

**The text change.** README.md#version gains a paragraph; VIEWS.md#audit names J19 among the findings and its action, to raise the subproject's language, after which the parent moves the pin.

**The validator rule.** J19, warning; source README Version, "A validator warns of a project that a recursive junction or a task's `subproject` field names whose `version.yaml`, read at the commit the linkage fixes, states a version before the parent's own, patch included". Entries `subproject-language-behind` (T5) and `tableaux-tooling` (T6). It joins the J family, beside J13, which reads the same `version.yaml` for the trunk; the ids are provisional.

**What tablo does today.** `j8` (`internal/validate/junctions.go:110`) reads `link.Project.Version` only to refuse a version the module does not accept, and nothing compares. `8118` Validator adds J19 after `j8` in `subproject`, for junction and task fields, once per task and link. `dada` Audit gives it the act `MovePin` and the assignee, as J13's row does.

**What the front ends meet.** Nothing in their code. The umbrella's validation shows four J19 warnings until the four subprojects state the umbrella's version and the pins advance.

**The version effect.** A new warning, no field: patch alone.

**The alternative.** Comparing the minor version alone is quieter, and leaves today's 0.3.2 against 0.3.1 silent, the very lag F25 found.

## Decisions at review

1. **The task-level field.** `subproject`, in the form a junction uses, stands for a recursive junction at each gate after the first that follows `undefined`. The task's own entry at a gate replaces it, and it is the task's own entry, so it lifts an ancestor's exemption. The alternative lets an ancestor's exemption win over the field, which makes the field the one statement in a task's own file that inheritance overrides.
2. **The status file under the field.** Unchanged: the file holds the gate, and the contributor advances it with the pin. The alternative derives the gate from the subproject's task, which needs two projects to share gate keys, a thing the method does not require, and removes the parent's status events.
3. **A parent's field.** An error, J18. The alternative passes it to the children as a default, so every child reads one subproject task.
4. **A moot reaffirmation.** README.md's example drops `Reaffirmed: c07d`. H7 warns of a trailer on a parent or on a leaf whose next junction is recursive, and the history keeps the event. The alternatives drop the example and add no rule, or keep the rule to the recursive leaf alone and leave the parent out.
5. **The unpinned requirement.** `commit` is optional on an absolute URL in a requirement alone. Absent, a tool reads the trunk tip that `version.yaml` names at the clone's default branch, and R14 reports the entry as information. No schema change. The alternative keeps the text's resolution, a requirement in the design that no tool sees.
6. **The lagging subproject.** J19 is a warning that compares major, minor and patch. It covers recursive junctions and the task's field in all three `url` forms, not requirements, and reports once per task and link. The alternative compares the minor version alone and leaves today's 0.3.2 over 0.3.1 silent.
7. **No version exemption for J19.** The rule applies whatever the parent's version, so `tableaux-tooling` gains four warnings at its present tag. The alternative exempts a parent before 0.4.0, as H6 exempts commits before 0.2.1, and hides the umbrella's present lag until it rises.
8. **The history's `subproject`.** The schema and the fields table gain the key, SYNTAX.md#history states the inline order with the project's own events first at one author time, and VIEWS.md reads inline. The alternative adds the key alone and leaves the order of ties to the corpus.
9. **The version.** 0.4.0, from F4 and F26. F13, F25 and the history fix are patch-level alone and ride on it. Only the entries that use a new form state 0.4.0. The alternative raises every entry to 0.4.0, as the move to 0.3.0 did, with about two hundred one-line changes and no new fact.
10. **The umbrella adopts the field.** Once a pinned tablo reads it, the four subproject tasks state `subproject` and drop their eight entries each. The alternative keeps the stated junctions, which stay valid.
11. **The field's place in the order.** Between `requires` and `junctions`, since the junctions replace it gate by gate. The alternative places it after `assignee`, which is where ac33's F10 may place `model`.
