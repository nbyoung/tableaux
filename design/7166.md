# Design 7166: Language clarifications

This design settles the seven points that remain at `7166`'s design gate. The trunk clarification (F19), the exemption rule (F7) and F14, F21, F22 and F23 already stand on the trunk, and this design does not reopen them. Every decision is a patch, and no rule id is new: each finding resolves into a sentence, a sharper reading of an existing rule, or a derived fact the corpus fixes.

- **F11.** History reads Git's default log, where a merge that takes one side's file changes nothing. The one exception is a merge on the trunk's first-parent line that brings in a task file. Authorisation reads that line, so the merge is an `authorised` event, as an `Authorised:` trailer is (decision 1).
- **F15.** S11 reads one commit: its files, and the `Reviewed:` commits its history holds, whichever came first. A history replays no rule (decision 2). SYNTAX.md's example breaks README.md's order, and it changes to a hand-off (decision 3).
- **F16.** A tool takes an id as its source text before the schema applies. T7 judges how the id is written, not the type YAML gives it (decision 4).
- **F17.** A leaf with no status file has a date and no recorder, and a `Reaffirmed:` commit dates nothing there (decision 5).
- **F18.** G12 and the schema's `contains` have required both states since 2026-09-29. The text now also says that a tool derives nothing from a file that fails G12 (decision 6).
- **F9.** The language does not change. S4 stands, and a status file at `undefined` carries a reason and a note (decision 7).
- **F8's remainder** concerns the tool alone. tabloio's `b618` already takes `review <id>… <gate>` (decision 8).
- **The version** goes to 0.3.3 if `7166` lands alone (decision 9).

## F11. Deciding commits and events disagree on merges

**The problem.** The deciding commit reads the trunk's first-parent history ([README.md#proposed-and-authorised-tasks](../README.md#proposed-and-authorised-tasks), line 82). On that line a `--no-ff` merge changes the task file against its first parent. The event commands of [README.md#history](../README.md#history) (lines 144–145) use the default log, and that log drops the same merge, since the merge is TREESAME to its second parent. A merge that authorises therefore leaves no event unless it carries `Authorised:` ([corpus/README.md](../corpus/README.md#findings-about-the-method), line 194). The worked example hides the gap, because its W4 carries the trailer.

**The rule.** The text uses two readings of "changes", and each reading has its own scope:

- In the history, a commit changes a file when the file differs from every parent's. Git's default log reads it this way. A merge that takes one side's file changes nothing of its own, and the commit that made the change keeps its event. For a status, that commit also keeps the date and the recorder.
- On the trunk's first-parent line, which authorisation reads, a commit changes a file when the file differs from its first parent's. There a merge that brings in a task file is the deciding commit, and it is an **`authorised` event** of the task, by the merger. A merge that also carries the trailer gives one event.

An `authorised` event judges no one, whatever its source. A trailer from someone who is not an authority is an event too, and authorisation decides whether either one accepts. Status files and pins stay on the default reading, so the merger never becomes a recorder.

**Example.** This is the history of `authorised-by-merge`. Pat proposes `c3d4` on `leaf`, records it there, and olive merges the branch with no trailer:

```yaml
- { date: 2026-09-02, commit: A2, by: pat@example.org,   task: "c3d4", event: task }
- { date: 2026-09-03, commit: A3, by: pat@example.org,   task: "c3d4", event: status, gate: defined, state: nominal }
- { date: 2026-09-04, commit: A4, by: olive@example.org, task: "c3d4", event: authorised }
```

The status keeps A3's date and pat as its recorder. A third command yields the merge:

```
git log --format='%as %h %ae' --first-parent --merges main -- .tableaux/tasks/9f31.yaml     # main is the trunk
```

**The text change.** README.md#history gains the two readings and the third command, and its `--no-ff` bullet says what the merge adds. SYNTAX.md#history gives the `authorised` row its second source. RULES.md names the derived fact.

**The validator or audit rule.** No rule changes. H4 reads "the newest event", so a merge that brings in a task file can now be that event, and the authority's merge then answers the hand-off that the history implies.

**What tablo does today.** `decide` walks first parents and reads `c.Changes`, which lists the changes against the first parent. It names the merge as the deciding commit with `ByMerge` (`internal/derive/authorise.go:186–199`). `Log.Changed` compares a path against every parent (`internal/history/log.go:56–82`), so `ownEvents` gives the merge no `task` event, and it makes `authorised` events from trailers alone (`internal/derive/events.go:237–269`). The history view's effect `authorised_merge` (`internal/views/history.go:191`) therefore never appears without a trailer. **Change.** In `internal/derive`, `ownEvents` adds an `authorised` event for a merge with `Trunk >= 0` whose `Changes` hold the task file. The event comes before the trailers, so the dedup at line 265 keeps one. In `internal/views`, `historyCommands` (`history.go:288`) gains the third command.

**What the front ends meet.** A history view shows one more line at such a merge, with the effect tablo already names. No front end changes.

**The version effect.** Patch. Only the meaning changes, and the event enum stays the same.

**The alternative.** Read every event on the first-parent line. A merge would then record every status its branch brings in, and the merger, often the owner, would become its recorder and owe its reaffirmations. Leaving the merge with no event keeps the gap the finding names.

## F15. The review may follow the status it validates

**The problem.** [SYNTAX.md#history](../SYNTAX.md#history) records `9f31` at `mockup` on 09-22 (line 538), and Ben reviews it on 09-24 (line 539). S11 rejects the status at every commit in between and accepts it at the tip, and the text does not say which reading holds ([corpus/README.md](../corpus/README.md#findings-about-the-method), line 198). [README.md#status](../README.md#status) already orders the steps (line 116): the contributor hands off with `review`, the reviewer commits `Reviewed:`, and then the contributor records the gate.

**The rule.** S11 reads one commit: its files, and the `Reviewed:` commits its history holds, before or after the commit that records the status. A validator applies it at the commit in view. A status recorded before its review is invalid at each commit until the review and valid from the review on. A history applies no rule at the commits it replays. It shows each status as the files at its commit state it, and the reviewer's line carries the effect `accepts`. README.md's order is the practice that keeps every commit valid, and the text says so.

The example does contradict that order. W7 passes the `mockup` junction, which has a reviewer, two days before W9 accepts it. The example now follows the order. W7 hands off at `defined` with `reason: review`, W9 accepts, and W10 records `function` past `mockup`:

```yaml
- { date: 2026-09-22, commit: b02e9c1, by: ada@example.org, task: "9f31", event: status, gate: defined, state: nominal, reason: review }
- { date: 2026-09-24, commit: 5d7a3f8, by: ben@example.org, task: "9f31", event: reviewed, gate: mockup }
```

The other order stays valid at the tip, and `review-after-status` fixes it. Pat's R2 passes `design` and olive's R3 accepts it. At `main`, `reviews` names R3. At the branch `recorded`, which stops at R2, the review has `commit: null`.

**The text change.** The README.md#status Review bullet gains the two sentences above and closes the order with "no commit of the order is invalid". SYNTAX.md#history gains one sentence before the example and the changed line. VIEWS.md#history says the status after each event applies no rule. The worked example's W7 and its event change to match.

**The validator or audit rule.** S11 stays an error. Its RULES.md row now reads "in the history of the commit in view, before or after the commit that records the status", and it gains the entry `review-after-status`. The audit adds no finding for the window, because the commits that make it do not change (VIEWS.md#audit, "Nothing resolves a finding about a commit").

**What tablo does today.** `s11` judges the source commit (`internal/validate/derived.go:255`). `accepted` and `reviews` take the oldest commit the source reaches that carries the trailer from the reviewer, as the files stand at that commit (`internal/derive/review.go:83–139`). The history view's `After` reads the status at each commit and applies no rule (`internal/views/history.go:144`). tablo already reads S11 this way, and nothing changes. tabloio's `b618` agrees: "`review` reads no status: a reviewer accepts before or after the status passes the gate" (`subprojects/tabloio/design/b618.md:302`).

**What the front ends meet.** Nothing new.

**The version effect.** Patch.

**The alternative.** Apply S11 at every commit of the trunk and report each window. That makes old history findings that nobody can fix. Keeping the example as it stands teaches an order that the text discourages.

## F16. An unquoted id fails the schema before the warning

**The problem.** [SYNTAX.md#tasksidyaml](../SYNTAX.md#tasksidyaml) says "A tool takes an id as a string whatever scalar YAML yields, and a validator warns of an unquoted id" (line 204). The schema types every id as a string (line 216). The text does not say whether the conversion comes before the schema, or what string the tool takes ([corpus/README.md](../corpus/README.md#findings-about-the-method), line 199).

**The rule.** At the four places a task file names an id, a tool takes the scalar's text as the file writes it, before it applies the schema. `0010` therefore stays `0010`, although YAML 1.2 reads it as 10 and YAML 1.1 as the octal 8. `07e0` stays `07e0`, although YAML 1.2 reads it as a float. T7 then warns of an id that the file writes in neither quotes, a block scalar nor `!!str`, whatever type YAML gives it. T6 checks the text against the pattern.

```yaml
# tasks/07e0.yaml
parent: { id: 0010, order: 1 }          # the parent "0010"; T7
# tasks/b2c9.yaml
requires:
  - { id: 07e0, from: defined, to: release, text: An id named without quotes }   # "07e0"; T7
```

**The text change.** The SYNTAX.md paragraph says where and what the tool converts. The RULES.md T7 row gains the reading and the entry `unquoted-id-text`. The corpus/README.md check paragraph reads "as its source text".

**The validator or audit rule.** T7 keeps its id and its severity, warning. Its source becomes the new SYNTAX.md sentences, and its entries are `unquoted-id` and `unquoted-id-text`.

**What tablo does today.** The Loader takes any scalar at the four places as a string whose text is the source text, before `Plain()` hands the schema a string (`internal/load/build.go:70–72, 164–168`). Design 4f60 says this "settles finding F16" (`design/4f60.md:222`). `t7` warns from `Quoted` and `Read`, so a plain `abcd` warns too (`internal/validate/tasks.go:60`). tablo already reads the rule this way, and nothing changes. `corpus/check.py` diverges in two places. It takes `str()` of the value, so `0010` becomes `"8"` and T9 fires. It warns only of a value that is not a string, so it misses `07e0` under pyyaml. The check.py draft takes each id's source text from the composed node.

**The version effect.** Patch.

**The alternative.** T7 could warn only where YAML yields something other than a string. The warning would then depend on the reader's YAML version, and an id that works today would turn invalid under a different reader.

## F17. The undefined leaf has a date but no recorder

**The problem.** [README.md#status](../README.md#status) dates a leaf with no status file by its task file's newest commit (line 104). The text does not say whether that commit's author is the recorder ([corpus/README.md](../corpus/README.md#findings-about-the-method), line 200).

**The rule.** The leaf has no recorder, since nobody has recorded a status. The date is the newest commit that changes the task file, read on the default log as F11 gives it. A `Reaffirmed:` commit dates nothing there: it is a `reaffirmed` event and confirms no status. The task definition and the tableau's provenance show the date alone. The work queue owes nobody a reaffirmation of the leaf, and its contributor at the first applicable gate after `undefined` finds it under work ready. The audit finds nothing stale there, as the owner ruled on 2026-10-07: "A leaf with no file has recorded nothing".

```yaml
"b2c9": { status: { gate: undefined, state: undefined, date: 2026-09-02, recorder: null, commit: U2 } }
# U3, pat's empty commit with Reaffirmed: b2c9 on 09-05, is an event and leaves the date at U2
```

**The text change.** The first paragraph of README.md#status gains the sentence. The VIEWS.md Status fact gains "dated by its task file and with no recorder". RULES.md names the derived fact.

**What tablo does today.** `leaf` gives an `Absent` status the newest change to the task file, with no trailer and no recorder (`internal/derive/status.go:135–143`). Design 27a3 decision 4 reads it this way and cites F17. The queue lists reaffirmations only for `Recorded` statuses (`internal/views/queue.go:207`). Nothing changes. `corpus/check.py` lets `Reaffirmed:` date such a leaf (`_status_commit`), and its draft stops that.

**The version effect.** Patch.

**The alternative.** The task file's author could be the recorder. That would give the author of every task file a reaffirmation owed for each leaf nobody has started. It would also contradict the 2026-10-07 ruling on stale statuses.

## F18. Nothing requires the `undefined` and `complete` states

**The problem.** The finding says that `gates.yaml` may omit the two states ([corpus/README.md](../corpus/README.md#findings-about-the-method), line 201). Since the corpus review of 2026-09-29, README.md#gates (line 37), the schema's `states: allOf: contains` and rule G12 require both, each with severity 0. The entries `gates-no-undefined-state` and `gates-complete-nonzero-severity` exercise them. The text still does not say what a tool does with a file that fails the rule.

**The rule.** G12 stays an error. A `gates.yaml` that fails G12 is one a tool cannot use, so the tool derives no status from it and gives no view. This is the 2026-10-07 ruling "A view stands beside an error", applied to an unusable `gates.yaml`. A tool never assumes a severity for a missing state.

**The text change.** README.md#gates gains one sentence. The RULES.md G12 row says that a tool derives no status from such a file.

**What tablo does today.** `g12` reports both faults (`internal/validate/gates.go:87`). `refusal` returns the part `states` for G7, G8, G9 and G12, and `statesRead` requires both keys at severity 0 (`internal/derive/derive.go:311, 345`). Nothing changes.

**The version effect.** Patch, for one sentence of meaning.

**The alternative.** A tool could derive with severity 0 for the missing state, as roll-up already ranks an unknown state. The views would then show a project whose gating the validator rejects.

## F9. No state before defined

**The problem.** S4 makes the gate `undefined` exactly when the state is ([README.md#status](../README.md#status), line 109). Work towards `defined` therefore has no state. The finding also says it has no reason, and calls itself minor ([PLAN.md#findings](../PLAN.md#findings)).

**The rule.** The language does not change, and the text says why. A state measures work against a definition. Roll-up sets `undefined` aside, so that a parent's state reflects defined work alone. Contrary to the finding, a reason already exists there: a status file at `undefined` may state one, with a note. The blockage tree and the queue read that reason as they read it at any other gate. The definition work itself is the task file's commits (PLAN.md D8), and the queue lists it under work ready at the first applicable gate.

```yaml
# status/b2c9.yaml
gate: undefined
state: undefined
reason: blocked
note: The definition waits for the sensor datasheet
```

**The text change.** The README.md#status S4 bullet gains the reason why, and points to the file at `undefined`.

**What tablo does today.** tablo accepts the file, and roll-up carries the reason to the root (`status-undefined-with-reason` passes). Nothing changes.

**The version effect.** Patch.

**The alternative.** S4 could let the state at `undefined` be any working state. That changes the schema's `allOf`, roll-up's step 1 and every view's `undefined` cell, which is a minor version for a minor finding.

## Decisions at review

1. **F11.** History reads Git's default log, and a merge on the trunk's first-parent line that brings in a task file is an `authorised` event. The alternative reads every event on the first-parent line, which makes the merger the recorder of every status it brings in.
2. **F15, the rule.** S11 reads the commit in view and accepts a review before or after the status, and a history applies no rule. The alternative applies S11 at every commit and reports each window.
3. **F15, the example.** SYNTAX.md's example and the worked example's W7 become a hand-off at `defined` with `review`. The alternative keeps the example and says that it breaks the order.
4. **F16.** A tool takes each id's source text before the schema, and T7 judges the writing, so a plain `abcd` warns. The alternative warns only where YAML yields something other than a string.
5. **F17.** A leaf with no file has a date and no recorder, and `Reaffirmed:` dates nothing there. The alternative names the task file's author as the recorder.
6. **F18.** F18 stands resolved by G12, and a tool derives nothing from a file that fails it. The alternative derives with an assumed severity of 0.
7. **F9.** S4 stands, and a reason at `undefined` says why the definition waits. The alternative lets the state at `undefined` take any working state, a minor version.
8. **F8.** The remainder belongs to tabloio's `b618`, which already takes several tasks, and F8 closes. The alternative keeps it open for a language change that nothing needs.
9. **The version.** Every decision is a patch: 0.3.3 alone, or whatever the wave composes. The alternative counts F11's new events as a minor change, although no file or field appears.
